Developer’s guide#

This is a collection of tutorials for developers. They are meant to be a practical guide to how to use Struphy for development purposes, such as implementing new features, propagators or models.

The tutorials give an overview of the most important classes used in writing new Propagators. These include classes for FEEC (finite element exterior calculus), particles and the coupling between them.

All notebooks are available at struphy-hub/struphy-tutorials (with a link to a predefined environment on binder) or within the Struphy source under tutorials/ (and in the built documentation under _collections/tutorials/). They can be run with Jupyter notebooks or Jupyter lab. It is recommended to use the same Python environment as for Struphy, e.g., by installing the Jupyter packages in the same environment.

Code formatting and import sorting#

Struphy uses ruff for formatting, linting and sorting imports (ruff’s I rules replace isort). The settings are in the [tool.ruff] section of pyproject.toml, and ruff is installed together with Struphy. Run the following from the repository root before pushing:

ruff check --fix    # lint and sort imports
ruff format         # format code

Both commands also handle the Jupyter notebooks in tutorials/. The CI fails if either of the following reports a problem:

ruff format --check
ruff check

To limit ruff to certain files or folders, pass their paths, e.g. ruff format src/struphy/models. Most editors can run ruff on save, e.g. the ruff extension for VS Code.

Auto-generated __init__.py files#

The files struphy/models/__init__.py, struphy/propagators/__init__.py and struphy/geometry/domains/__init__.py are generated from the classes defined in these packages. After adding, renaming or removing a model, propagator or domain, regenerate them with:

struphy build-init-files

This command is only available when Struphy is installed in editable mode, and it formats the generated files with ruff.

Models are defined by their equations#

A Struphy model is defined by the PDE system in its docstring (doc_pde), not by its discretization. Before adding a new model, check the docstrings of the existing models (Models) for the same equations:

  • Same equations, new discretization (other solution spaces, propagators, solvers or time stepping): no new model is created. The new discretization is added to the existing model through model flags (constructor arguments) or propagator options.

  • Existing equations plus a new term (e.g. a dissipative term added to the MHD equations): a new model is created that inherits from the existing one. It adds the propagator(s) for the new term and shows the extended PDE system, including the new term, in its own doc_pde.

  • There are no flags or options that switch propagators, i.e. terms of the equations, on or off. A model with a term switched off is a different model, and this is expressed by inheritance as above.

Inheritance in practice (see e.g. Vlasov → VlasovAmpereOneSpecies → VlasovMaxwellOneSpecies):

  • The model’s __init__ stores its arguments with self._store_params(locals()) and then calls super().__init__(...). The parent runs the steps of _setup() through hooks, which the new model extends by calling super(): _create_species (new species), _propagator_args (constructor arguments of Propagators), _link_propagator_variables (variables of the new propagators) and _create_scalars (new scalars, e.g. the energy of a new field, added to en_tot).

  • The inner class Propagators of the new model inherits from the parent’s Propagators. Its __init__ calls super().__init__(**kwargs) and adds the propagators of the new terms as attributes.

  • The splitting order is the attribute order. To change it, Propagators defines a tuple splitting_order with the names of all propagators, as class attribute or in its __init__ (see apply_splitting_order()).

  • Species classes inherit too, e.g. class EMFields(VlasovAmpereOneSpecies.EMFields) declares b_field and then calls super().__init__(), whose init_variables() includes it. Variables and scalars keep their names along the chain.

  • doc_discretization is generated from Propagators (the propagators in splitting order, with their docstrings). A model overrides it only to describe its time stepping in the docstring and returns cls.propagators_doc().

  • A propagator whose term vanishes for the given input (e.g. PushVxB without magnetic field) does nothing, instead of being switched off by a flag.

  • Consecutive propagators that must be integrated symmetrically (second order in time, e.g. steps that are exact in time each but do not commute) are listed in the class attribute strang_groups of Propagators (a tuple of tuples of names). Each group is one block of the splitting, integrated with Strang splitting over its members, the last member in the middle (see splitting_blocks()). Child models inherit it and override it when they change a group.

Anatomy of a model#

This section follows the construction of VlasovMaxwellOneSpecies (VM), which inherits from VlasovAmpereOneSpecies (VA), which inherits from Vlasov. Each class only contains what it adds to its parent:

Vlasov

VlasovAmpereOneSpecies

VlasovMaxwellOneSpecies

arguments

base_units, charge_number, mass_number

+ alpha, epsilon

+ measure_gauss_law

species

kinetic_ions (KineticIons, variable var)

+ em_fields (e_field, phi)

+ b_field in em_fields

propagators

push_vxb, push_eta

+ coupling_va

+ maxwell

splitting order

push_vxb, push_eta

push_eta, push_vxb, coupling_va

maxwell, push_eta, push_vxb, coupling_va

scalars

en_f

en_E, en_f (with \(\alpha^2\)), en_tot

+ en_B (also in en_tot), gauss_error

VlasovMaxwellOneSpecies(alpha=1.0) runs the following steps. Since self is the VM instance, every self.<hook>() and self.EMFields, self.Propagators resolves to the VM version, which calls the parent’s version with super() and extends it:

VM.__init__
 ├─ 0. self._store_params(locals())       stores VM's arguments (incl. alpha, measure_gauss_law);
 │                                         the parents' calls below do not overwrite them
 └─ super().__init__(...)  -> VA.__init__
     ├─ self._store_params(locals())       (no effect, already stored)
     ├─ super().__init__(...)  -> Vlasov.__init__
     │   ├─ self._store_params(locals())   (no effect)
     │   └─ self._setup(base_units)        StruphyModel._setup:
     │       ├─ 1. self._create_species()          VA:     self.em_fields = self.EMFields()   (VM's EMFields: e, phi, b)
     │       │                                     Vlasov: self.kinetic_ions = self.KineticIons(alpha=1.0, ...)
     │       ├─ 2. self.setup_equation_params()    units, alpha, epsilon of the species
     │       ├─ 3. self.Propagators(**self._propagator_args())
     │       │      VM._propagator_args() -> {"b2_var": b_field}
     │       │      VM.Propagators -> VA.Propagators -> Vlasov.Propagators(b2_var): push_vxb, push_eta
     │       │                        VA: + coupling_va,  VM: + maxwell,  then reordered by splitting_order
     │       ├─ 4. self._link_propagator_variables()   Vlasov, then VA, then VM link their propagators
     │       └─ 5. Scalars(**self._create_scalars())    VA: en_E, en_f, en_tot;  VM: + en_B, new en_tot
     └─ self._create_initial_poisson(...)   VA, after the parent steps (helper defined in Vlasov)

Helpers that several models of a chain need go into the first class of the chain that can hold them. For example, Vlasov holds the initial Poisson solve (_create_initial_poisson, _solve_initial_poisson) and the Gauss-law diagnostic (calculate_gauss_error), which VA, VM, VMQN and the linear models use; Vlasov itself does not call them.

When writing a new model in a chain:

  • call self._store_params(locals()) before super().__init__(...), and pass the parent’s arguments on;

  • override only the hooks that change, and call super() in them;

  • in Propagators, call super().__init__(**kwargs) and document in its docstring that further keyword arguments go to the parent’s Propagators;

  • annotate the attributes whose class the model changes (em_fields: EMFields, propagators: Propagators), so that IDEs see the model’s classes, not the parent’s;

  • write doc_pde for the complete PDE system of the new model, not only the new terms.

Docstrings of models and propagators#

Models and propagators are documented at two levels of detail. A model states the physics, and its propagators state the mathematics and numerics. The propagator docstrings are embedded in the model documentation (doc_discretization), so together they describe the model from the PDE down to the time stepping.

Models (doc_pde and doc_scalar_quantities) are written in the style of a physics textbook:

  • doc_pde always shows the PDE system solved by the model, in strong form and with the usual physics notation (e.g. \(\nabla \times\), \(\nabla \cdot\), \(\mathbf v \times \mathbf B\)). It names the unknowns and the parameters (as defined in doc_normalization), but contains no solution spaces, weak formulations or discrete operators. These belong to the propagators.

  • If the system has conserved quantities, such as energy, momentum, magnetic helicity, mass or charge, they are always stated as formulas (e.g. \(\frac{d}{dt} \frac{1}{2} \int (|\mathbf E|^2 + |\mathbf B|^2)\,\textrm d \mathbf x = 0\)), in doc_pde below the equations under a heading Conserved quantities, together with the conditions under which they hold (e.g. boundary conditions, absence of sources). doc_scalar_quantities lists the scalars tracked during a simulation.

Propagators are more mathematical. The class docstring always contains three sections:

  1. Continuous problem: the substep solved by the propagator, stated for the unknowns that it updates, with their solution spaces (e.g. \(\mathbf E \in H(\textrm{curl})\), \(\mathbf B \in H(\textrm{div})\)) and the weak formulation where one is used (find \(\mathbf E \in H(\textrm{curl})\) such that … for all \(\mathbf F \in H(\textrm{curl})\)).

  2. Semi-discrete problem: the space-discrete version of the substep, as a system for the FE coefficients and/or the markers. Every operator that appears (mass matrices, discrete derivatives, projectors, basis operators, accumulation matrices, …) is defined or referenced, e.g. with :class: or :ref: links into the documentation.

  3. Time discretization: all available time-stepping options (e.g. implicit midpoint/Crank-Nicolson, explicit Runge-Kutta with Butcher tableau, discrete gradient, analytic solution), each with its update formula, the option that selects it and the linear or nonlinear solver it requires.

Notation of mass matrices. Mass matrices are written as \(\mathbb M^\alpha_{w}\): the superscript \(\alpha \in \{0, 1, 2, 3\}\) denotes the space of the de Rham sequence (\(v\) for \((H^1)^3\), two indices such as \(\mathbb M^{21}\) for mixed matrices), the subscript \(w\) the weight under the integral, e.g. \(\mathbb M^2_{\rho_0}\) for \(\int \rho_0 \mathbf W \cdot \mathbf V \,\textnormal d \mathbf x\) or \(\mathbb M^2_{B_0}\) for \(\int (\mathbf B_0 \times \mathbf W) \cdot \mathbf V \,\textnormal d \mathbf x\). Unweighted mass matrices have no subscript (\(\mathbb M^1\)). In mixed matrices, the first index is the space of the test functions (rows), e.g. \(\mathbb M^{21}_{J_0}\) (M21J, weight \(\mathbf J_0 \times\)) maps 1-forms to 2-forms. A weight that is too long for the subscript may be abbreviated (e.g. \(\mathbb M^2_\perp\)) if it is written out next to the symbol. The space is always the superscript and the weight always the subscript; give the corresponding attribute of WeightedMassOperators (e.g. M2n, M2B) next to it.
